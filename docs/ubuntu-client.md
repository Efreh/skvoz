# Клиент Ubuntu

`skvoz-client` 2.0.0 — приложение Rust с GTK4/libadwaita для Ubuntu 24.04+
на amd64. Поддерживает локальные интерфейсы HTTP/CONNECT/SOCKS5 CONNECT
и передачу IPv4/IPv6-пакетов через TUN.
Оба используют комплектный `skvoz-network-runtime` 0.1.0 с тем же Core 3.1.0.
GTK управляет соединением; TCP и packet I/O находятся в
[общем сетевом модуле](network-runtime.md). Установленному приложению не нужны
Rust или Python.

Новая интеграция требует отдельной проверки собранного deb, GUI и реального
сервера. Детерминированные проверки исходников не подтверждают установку
маршрутов, DNS, восстановление после аварий или скорость в целевом окружении.

## Установка и подключение

После публикации соответствующей версии загрузите deb и `.sha256` из **Releases**
репозитория, релиз **SKVOZ Ubuntu**. Наличие workflow не означает, что новая версия
уже опубликована. В каталоге загрузки:

```sh
sha256sum -c skvoz-client_2.0.0_amd64.deb.sha256
sudo apt install ./skvoz-client_2.0.0_amd64.deb
```

Откройте **SKVOZ**, введите IP/DNS сервера, внешний порт NATS, логин и пароль.
IPv6 допускает `::1` или `[::1]`; порт вводится отдельно.
Выберите режим в настройках и нажмите **Подключиться**. По умолчанию выбран
режим «Прокси». Устройство выделяется автоматически; ручной peer_id не нужен.
Сервер должен поддерживать [enrollment 2](#протокол-выделения-устройства-v2),
network 2, API 1, runtime 0.1.0 и Core 3.1.0.

TLS проверяет системные корни и исходное имя/IP сервера.
Для private CA укажите PEM-файл, полученный от администратора по доверенному
каналу. CA по сети не загружается; проверка TLS обязательна. Закрытая копия
CA используется для enrollment и Core.
[Профиль транспорта](nats-runtime.md#профиль-транспорта) общий с сервером.

Пароль сохраняется после **Подключиться** и остаётся после отключения/ошибки.
Он связан с нормализованными адресом, портом и логином. Пароли хранятся открытым
текстом в закрытом `settings.json` (`0600`, каталог `0700`); системное password
store не используется. Неподдерживаемый или неполный формат настроек отклоняется.
Старые настройки автоматически не мигрируются.

## Два режима

В режиме **Прокси** приложение-потребитель выбирает локальный адрес:

| Тип | Адрес по умолчанию |
| --- | --- |
| HTTP и HTTPS через CONNECT | `http://127.0.0.1:8080` |
| SOCKS5 CONNECT с DNS на сервере | `socks5h://127.0.0.1:1080` |

Кнопка справа копирует полную URI. Порты 1024–65535 должны различаться;
их изменение требует отключения. Открытие двух listener атомарно: при занятом
порте второй закрывается. Loopback listener не требует локальной аутентификации
и доступен процессам других пользователей машины. Закрытый control API имеет
отдельную защиту и не изолирует доступ к TCP listener.

HTTP поддерживает абсолютное `http://host:port/path`, передаёт тело и ответ.
Routing/authentication headers адаптера не отправляются целевому сервису;
CONNECT передаёт непрозрачные TCP-байты без расшифровки прикладного TLS.
SOCKS5 поддерживает только TCP CONNECT, без BIND/UDP ASSOCIATE.
Неоднозначные HTTP headers/body length отклоняются. Handshake ограничен
10 секундами / 64 КиБ, 256 заголовками и 256 Connection nominations.
Назначения и DNS проверяет серверная policy; private/localhost требуют явного allow.

В режиме **ВПН** передаются полные L3 IPv4/IPv6-пакеты: TCP, UDP, ICMP и другие
допущенные policy протоколы. Ethernet/L2 и multicast не включены.
Выбор семейств `[4]`, `[6]`, `[4,6]` должен соответствовать серверному backend;
по умолчанию запрашиваются оба семейства. Отсутствующее семейство вызывает
явный отказ, автоматического исключения IPv6 нет. MTU по умолчанию 1500,
для IPv6 минимум 1280. Смена режима требует остановки, очистки и нового подключения.

Настройку сети выполняет узкий root helper с разрешением polkit до открытия IP-сессии.
Helper настраивает только собственный TUN, маршруты, per-link DNS и drop guard;
GTK/runtime остаются процессами пользователя. Прямой транспорт использует
подтверждённый IP брокера и заданный TCP-порт с проверкой исходной TLS identity.
Во время capture скрытого DNS refresh брокера нет.

При аварии guard остаётся: приложение не переключает захваченный трафик
автоматически на обычную сеть. Новый authorized owner сначала восстанавливает
собственное состояние, затем использует закрытый сохранённый snapshot брокера.
Отсутствующий или несовпадающий snapshot требует явного **Отключиться** для
восстановления сети. Ручная остановка снимает guard после подтверждённой очистки;
неуспешная очистка отображается как ошибка. Перезагрузка, смена uplink, другое
ПО, управляющее сетью, и сбой helper/kernel требуют отдельной проверки платформы.

## Фоновая работа и индикатор

Закрытие окна скрывает приложение; соединение продолжается до **Отключиться**
или **Завершить SKVOZ**. Повторный запуск открывает существующий экземпляр.
Меню индикатора содержит окно, подключение/отключение, состояние, скорость,
журнал, настройки и выход. StatusNotifierItem/AppIndicator использует GIO/DBusMenu.
При отсутствии indicator host скрытый запуск показывает окно.

В настройках независимы autostart и подключение при запуске, оба выключены
по умолчанию. Журнал включён, текст скорости рядом с индикатором выключен.
Порты, CA, режим и IP-параметры меняются после отключения.
Автоподключение не отменяет ручного отключения в текущем сеансе.

## Скорость и журнал

Окно и меню показывают `↓`/`↑` в КиБ/с. Значения вычисляются раз в секунду
из счётчиков общего runtime: отправленные байты приняты Core, полученные
фактически записаны в локальный socket/TUN. Служебные NATS/TLS bytes и отброшенные
пакеты не учитываются. Это полезная передача приложения, не physical interface rate.

Компактный журнал показывает последние десять событий, **Подробнее** — полную
историю до 500 событий в памяти. Для TCP доступны runtime-local номер,
HTTP/CONNECT/SOCKS5/TCP, хост/порт и итог с байтами направлений.
Path/query, headers, credentials и содержимое не сохраняются.
CONNECT/SOCKS5 показывают внешнее назначение, не вложенные HTTP-запросы.
События передачи IP-пакетов не превращаются в журнал каждого сетевого flow.
Отключение журнала или **Очистить** удаляет историю.

Результаты runtime: `opening`, `active`, `finished`, `cancelled`, `forbidden`,
`overloaded`, `network_unavailable`, `timeout`, `local_setup_failed`,
`invalid_request`. Это локальное наблюдение; для первичного источника отказа
сопоставляйте время с [серверным журналом](server-connector.md#диагностика).

## Устройство, процессы и восстановление

`$XDG_CONFIG_HOME/skvoz` (или `~/.config/skvoz`) хранит private settings версии 2,
пароли, device tokens и ограниченный transport cache. Cache связан с адресом,
портом, логином и конкретным устройством. Один экземпляр владеет блокировкой;
временное состояние выбирает `$XDG_RUNTIME_DIR`, иначе системный temp directory.
Runtime получает секреты через private файл, удаляемый после HELLO,
и управляется через socketpair API 1. Прикладные данные через этот JSON не идут.

После потери Core новые потоки требуют нового соединения; прежние байты не
возобновляются. В режиме «Прокси» приложение может создать новый runtime.
В режиме «ВПН» восстановление сначала учитывает guard/helper, используя сохранённое
назначение транспорта. Недоступные credentials/сертификат/версия требуют
исправления настроек. Явное отключение завершает runtime и выполняет RESTORE
только после cleanup.

Deb содержит `/usr/lib/skvoz-client/skvoz-client`, общий runtime,
`/usr/libexec/skvoz-network-helper`, systemd socket/service instances и policy
`org.skvoz.network.manage`. Installer создаёт root config/state и socket instance
для существующих обычных локальных пользователей. Пользователь, добавленный
после установки, требует административного provision соответствующего UID:
root-owned `/etc/skvoz-network-helper/<uid>.json` и
`/var/lib/skvoz-network-helper/<uid>` (`0700`), endpoint directory
`/run/skvoz-network-helper/<uid>` (`0711`) и
`skvoz-network-helper@<uid>.socket`. Config helper:

```json
{"v":1,"role":"client","state_dir":"/var/lib/skvoz-network-helper/1000","policy":null}
```

Файл имеет права `0600`. Замените UID примером своего пользователя; изменения
systemd выполняет администратор. Удаление пакета требует штатной остановки
helper и отсутствия guarded/prepared journal; аварийное состояние не объявляется
безопасно восстановленным по одному отсутствующему процессу.

## Протокол выделения устройства v2

Enrollment request версии 2 связывает private случайный device token с
broker-authorized reply subject. Request строго ограничен, повторные/неизвестные
поля и произвольный reply отклоняются. Ответ успешного сервера:

```json
{"v":2,"namespace":"skvoz.application","peer_id":2,"network_runtime":{"network":2,"api":1,"version":"0.1.0","core":"3.1.0"}}
```

Повтор token идемпотентен, в том числе после потерянного ответа/перезапуска.
Сервер подтверждает ACL и durable state до ответа.
Все устройства логина используют общие credentials: разные PeerId этого
логина не дают взаимной credential isolation. `user add`, ручная выдача и
автоматическое enrollment занимают один общий device pool.
Ошибки: `device_limit`, `overloaded`, `invalid_request`, `enrollment_failed`.
Подробности и управление пользователями — в [руководстве сервера](server-connector.md).

## Границы ресурсов

Клиентский профиль имеет 32 Core streams, одну IP-сессию, окно 64 КиБ и
max frame 16 КиБ. IP control + один data channel оставляют 30 TCP-слотов.
Runtime budget 16 МиБ / 4096 records и конечные API/packet queues ограничивают
логические буферы; это не предел RSS, CPU или число пользователей сервера.
Системные resolver/socket/kernel allocations требуют отдельного измерения.
Кредит возвращается после фактической записи; partial SEND удерживает остаток.
Точные пределы и сроки — в [общем контракте](network-runtime.md#данные-кредит-и-границы).

## Сборка и проверки

На Ubuntu нужны Rust 1.92, GTK4/libadwaita development packages, pkg-config и GCC:

```sh
sudo apt install libgtk-4-dev libadwaita-1-dev pkg-config build-essential librsvg2-common
cargo build --release --locked -p skvoz-ubuntu-client -p skvoz-network -p skvoz-network-helper --features skvoz-network/linux-runtime
clients/ubuntu/packaging/build-deb.sh
cargo test --release --locked -p skvoz-ubuntu-client --lib
SKVOZ_UI_TEST=1 dbus-run-session -- xvfb-run -a cargo test --release --locked -p skvoz-ubuntu-client --test ui -- --nocapture
```

Для source-only проверки без GTK:

```sh
cargo test --locked -p skvoz-ubuntu-client --no-default-features --lib --features skvoz-network/linux-runtime
```

UI требует Xvfb, D-Bus и GTK runtime; реальные process fixtures требуют также
NATS, Ruby/Bundler серверного компонента и curl. Проверочный driver включается
feature `qualification` и не входит в deb. Реальные сценарии workflow и RSpec
проверяют собранные процессы отдельно от детерминированных тестов;
их наличие не означает, что новая интеграция уже прошла все сценарии.
Process RSpec запускаются с UID/GID 10001, пустыми capabilities и
`no-new-privileges`, поскольку настоящий fixture server проверяет эту границу.
Workflow использует `setpriv`; обычный графический клиент работает от
пользователя рабочего стола.

Workflow **Ubuntu client** компилирует клиент, общий runtime и helper, собирает
и проверяет deb. После успешной сборки `main`/`master`, включая ручной запуск
на этих ветках, deb и SHA256 автоматически публикуются в **Releases** с тегом
`ubuntu-v<version>-build.<run_number>`. Номер сборки отличает релизы одной версии
приложения; версия внутри deb остаётся из `clients/ubuntu/Cargo.toml`.
Push тега `ubuntu-v<version>` также публикует пакет, проверяя совпадение версии.
Pull request и ручной запуск другой ветки проходят проверки без публикации.

Пакет сначала загружается в черновик, затем релиз становится доступен.
Повторный запуск продолжает незавершённый черновик; уже опубликованный релиз
с тем же тегом не изменяется. После успешной публикации остаются пять последних
опубликованных клиентских релизов по времени публикации. Более старые релизы
удаляются вместе с deb/SHA256; Git-теги сохраняются. Серверные релизы `v*`
и черновики не удаляются. Публикации клиента выполняются последовательно;
при ошибке загрузки или публикации очистка не запускается. Отдельные копии
пакетов в Actions artifacts не сохраняются.

Положительные path filters исключают
обычные client source/UI/package изменения из серверной сборки. Общие
`Cargo.toml`, `Cargo.lock`, Core/network/daemon и метаданные `clients/ubuntu/Cargo.toml`
затрагивают зависимые сборки. Серверному Docker-build достаточно этого manifest
и пустых Cargo targets: его образы не собирают клиент и не содержат GTK.
Реальное выполнение нового удалённого workflow и публикация Release проверяются
после публикации соответствующего изменения; локальная сборка этого не доказывает.
